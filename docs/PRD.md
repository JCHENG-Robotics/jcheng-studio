## 0. 文档约束与证据等级

本 PRD 是拟建系统的需求，不表示功能已存在。下列状态必须区分：`Verified in source`（静态源码确认）、`Hardware validated`（实机验证）、`Proposed`（计划）、`Unknown`（待核实）。不得将源码有 API 等同于实机行为合格。

**已知输入**：厂商 `ros_robot_controller_sdk.py` 为 Python 串口 SDK，提供总线舵机位置命令、位置读取、停止、扭矩及部分状态读取接口；存在厂商 ROS 2 Driver；项目规划以真实 ArmPi 控制、模型修正、标定、视觉抓取、误差预算和可靠性实验为核心。**尚未确认**：驱动实际 Topic/Service/Action、位置反馈频率与精度、硬件限位、控制板固件协议细节、部署拓扑、急停硬件条件、轨迹执行支持情况。所有未确认项必须先做只读审计或安全实机验证。

本 PRD 不替代 `MASTER_PLAN_V3_PRIVATE.md` 和 `ROADMAP_PUBLIC.md`；若冲突，以 Board 最终决定为准。不得将私有计划中的申请/时间/预算信息直接复制到公开仓库。

## 1. 产品愿景与边界

### 1.1 一句话定义

ArmPi Debug Studio 是以**可解释、可追溯、可安全操作**为中心的机器人开发控制台：把控制命令、关节反馈、ROS 2 运行状态、SDK 通信事件、轨迹误差及实验记录关联在同一时间轴上，使开发者能回答“发送了什么、实际发生了什么、为什么偏离、如何复现”。

### 1.2 目标用户与场景

- **主要用户**：单人机器人系统开发者（本项目 Board），在实验台前或通过局域网浏览器进行调试。
- **场景 S1：首次连接**：检查设备、ROS 图、驱动与反馈；禁止未经校验直接运动。
- **场景 S2：关节调试**：安全移动单关节/多关节，核对零位、方向、角度映射和机械限位。
- **场景 S3：异常定位**：定位“发了命令却没动”“超时”“反馈异常”“ROS 节点掉线”。
- **场景 S4：轨迹分析**：将规划轨迹、实际下发命令、反馈曲线与事件对齐，量化偏差。
- **场景 S5：实验复现**：记录配置、样本、误差与失败代码，导出可复核数据。

### 1.3 产品成功标准

1. 无需同时翻阅多个终端，即可在一个界面判断系统当前能否安全进入调试。
2. 每次运动命令均有操作者、参数、时间、控制源、响应及结果记录。
3. 通信/驱动故障能够被明确标记为 `Unknown/Degraded/Fault`，不以缺失数据伪装正常。
4. 目标与反馈可在同一时间基准下比较；误差指标附带采样质量与测量局限。
5. 实验导出可关联软件版本、配置、标定版本和原始数据。

### 1.4 非目标

- 不重写 MoveIt 2、ROS 2、串口协议或厂商 SDK，除非测量证明必须替换。
- 不宣称浏览器提供硬实时控制；不以 UI 按钮替代实体急停/断电。
- 不在 MVP 中加入 AI 自动操控、VLM、强化学习、SLAM 或移动底盘控制。
- 不将厂商工具的所有功能原样复制；只实现本项目调试所需的最小功能。
- 不承诺远程公网控制、无人值守运动或跨网络实时遥操作。

## 2. 优先级与交付阶段

优先级定义：`P0` MVP 必须；`P1` 稳定后高价值；`P2` 扩展；`Out` 明确不做。阶段门槛为**验收条件**，不是日历承诺。

| 阶段 | 范围 | 进入下一阶段的门槛 |
|---|---|---|
| G0 — Read-only Discovery | 厂商接口审计、环境与设备探测、模拟数据源、危险命令隔离 | 接口清单和风险清单通过评审；不需要真实运动 |
| G1 — Safe Debug MVP（P0） | 连接/状态、控制权、限位、关节调试、日志、故障状态、基础数据存储 | 安全实机验收通过，失联/超时/拒绝动作均可复现 |
| G2 — Trajectory Inspector（P1） | 规划/命令/反馈对齐、误差图、事件时间轴、轨迹回放 | 轨迹记录完整、指标可复算、异常标注可定位 |
| G3 — Experiment Lab（P1） | 试验定义、重复性/回差/标定记录、CSV 与 rosbag2 引用、对比分析 | 试验可复现、导出字段完整、统计口径固定 |
| G4 — Visual Workbench（P2） | URDF 3D、TF 检查、相机叠加、更多诊断工具 | 不影响 G1–G3 安全与稳定性 |

**范围冻结**：未通过 G1，不启动 G2 的真实机器人执行功能；G2/G3 可先基于离线记录开发。

## 3. 关键用户工作流

### WF-01 连接与诊断（P0）

1. 用户打开 Dashboard；系统默认 `Disconnected / Read-only`。
2. 用户选择连接配置（设备/ROS Domain/驱动模式），仅进行发现与探测。
3. 页面显示串口是否可用、驱动是否在线、状态反馈新鲜度、关节映射版本、限位是否已验证、物理安全前置条件。
4. 未满足运动门槛时只能查看诊断；页面解释阻止原因和排查步骤。
5. 通过安全检查后，用户显式申请本地控制权，才能进入可操作状态。

### WF-02 单关节点动/目标位置（P0）

1. 选择关节，显示关节名、舵机 ID、目标角、反馈角、原始舵机值、已验证限位及当前数据年龄。
2. 用户输入目标和保守时长；前端预校验，后端再次校验；超限或状态过期直接拒绝。
3. 必须通过显式“预览 → 确认执行”，默认不允许滑块拖动即连续发运动命令。
4. 记录命令 ID、请求时间、下发时间、反馈采样、最终状态；超时进入 `Unknown/Fault` 而不是自动重试。
5. 停止命令可见且易操作；物理断电/急停仍是独立的最终防护。

### WF-03 运动异常诊断（P0）

1. 故障出现时冻结关键事件索引，不丢弃最近缓冲区。
2. 用户从时间轴选择事件，查看命令参数、ROS 调用、SDK 错误、串口状态、反馈时间戳和诊断建议。
3. 故障恢复需要重新确认控制权与安全前置条件；不得自动恢复运动。

### WF-04 轨迹检查（P1）

1. 导入/订阅 MoveIt 2 规划轨迹及执行结果。
2. 记录计划点、实际发送点、真实反馈；三者分别命名，禁止将“已发送”标为“已执行”。
3. 展示逐关节目标/反馈、误差、延迟、采样间隙、失败事件。
4. 支持离线回放；回放默认绝不向硬件发命令。

### WF-05 实验记录（P1）

1. 创建实验定义：目的、方法、硬件配置、标定版本、关节映射、试验参数与停止规则。
2. 按 `trial_id` 记录目标、测量、执行结果、异常、数据文件及操作者备注。
3. 支持成对实验的 `pair_id`、方法顺序和失败代码。
4. 导出 CSV + 元数据 JSON + 可选 rosbag2 路径引用；保留原始数据和分析版本。

## 4. 页面与信息架构

**全局导航**：Dashboard / Joint Control / Diagnostics / Trajectory Inspector / Experiment Lab / Settings。

**全局顶栏（任何页面可见）**：机器人身份、数据源（Live/Simulation/Replay）、连接状态、控制权持有者、最近反馈年龄、故障级别、只读/可控状态、停止入口。`Replay` 和 `Simulation` 必须有显著标识，禁止误认真实设备。

| 页面 | 必须显示 | 操作边界 |
|---|---|---|
| Dashboard（P0） | 连接链路、设备/驱动状态、关键告警、最新事件 | 默认只读 |
| Joint Control（P0） | 关节表、目标/反馈、单位转换、限位、动作预览 | 控制权+安全检查后可操作 |
| Diagnostics（P0） | ROS 图、串口状态、SDK 错误、反馈年龄、温度/电压（有数据才显示） | 诊断与安全恢复 |
| Trajectory Inspector（P1） | 规划/命令/反馈曲线、误差、时间轴、回放 | 离线回放不驱动硬件 |
| Experiment Lab（P1） | 实验方案、试验列表、失败代码、导出与比较 | 实验执行受同一控制门禁约束 |
| Settings（P0） | 设备配置、关节映射、限位来源、日志策略、权限 | 危险配置变更需确认并审计 |

界面原则：状态文字不能只靠颜色表达；所有单位显式标注；时间轴允许缩放与筛选；错误信息必须可复制；关键状态应展示更新时间与来源；移动端默认只读（未来如支持控制须独立安全评审）。

## 5. 功能需求与验收标准

### FR-01 设备与数据源管理（P0）

- 支持 `Disconnected / Connecting / ReadOnly / Ready / Executing / Degraded / Fault / EStopOrPowerCutReported / Replay / Simulation` 等状态；真实急停状态只有存在可信硬件信号时才能确认，否则显示 `Unknown`。
- 明确区分“串口可打开”“驱动进程在线”“收到新鲜反馈”“硬件可安全运动”。
- 连接中断后立即撤销新的运动许可；重连不自动恢复执行。
- **验收**：拔掉连接、停止驱动、停止反馈三种故障分别触发正确状态和可读诊断；恢复后需人工重新授权。

### FR-02 关节映射与单位（P0）

- 配置 `joint_name ↔ servo_id ↔ raw_value ↔ radians`，包括方向、零位、有效范围和来源。
- 原始舵机值到 rad 的映射必须可配置、可版本化，并通过安全实机测量验证；不得假定所有舵机都是固定线性 `0–1000 ↔ ±π`。
- 区分 `provisional` 与 `hardware_verified` 限位；未验证时只允许保守受限测试模式，具体门槛需硬件安全评审。
- **验收**：边界值、非法 ID、NaN、单位错误、反向映射、超限目标均被拒绝并写入日志。

### FR-03 安全关节操作（P0）

- 单关节目标、多关节目标、保守速度/时长、预设安全姿态（须经实机确认）、夹爪命令（验证接口后启用）。
- 禁止滑块拖动即连续发送；高频点动需独立设计死手控制和失联保护，MVP 默认不提供。
- 后端独立检查：控制权、状态新鲜度、限位、最大步长、速度/时长、工作区与碰撞约束（如有可信模型）。
- **验收**：无控制权、状态过期、非法目标、运行中冲突请求均拒绝；拒绝原因可追踪。

### FR-04 控制权仲裁（P0）

- 同一时刻只能有一个运动命令源拥有控制权；明确 Web UI、厂商 Demo、MoveIt 执行器之间的排他策略。
- 控制权租约具备到期时间与心跳；失联时撤销新命令许可，机器人侧按已验证的安全策略停止或进入故障态。
- 禁止 Web 后端与 ROS Driver 直接争抢同一串口；推荐唯一硬件拥有者进程。
- **验收**：两个浏览器/外部控制器竞争时仅一个可写；租约过期、进程退出后无隐式接管。

### FR-05 诊断与故障状态（P0）

- 显示 SDK/驱动错误、串口连接、反馈延迟、温度/电压/扭矩（只在 API 和实机验证后启用）、ROS 节点与关键接口状态。
- 告警分级 `Info / Warning / Fault / Critical`，每条包含时间、来源、错误码、上下文、推荐排查步骤。
- 缺失传感器/接口必须显示 `Unavailable`，不得虚构正常值。
- **验收**：可用模拟故障注入覆盖超时、空反馈、异常值、断线、节点退出。

### FR-06 事件与命令审计（P0）

- 记录 `event_id`、`command_id`、时间戳（墙钟与单调时钟）、来源、目标、结果、错误、软件版本、配置版本。
- 区分 `Requested / Validated / Dispatched / Acknowledged / Observed / Completed / Failed / Unknown`；各状态只能基于明确证据转移。
- 日志不可通过普通 UI 操作静默覆盖；提供过滤、复制、导出与隐私脱敏。
- **验收**：每次命令可追踪完整状态或明确的未知状态；故障后保留前后关联事件。

### FR-07 轨迹分析（P1）

- 支持 `JointTrajectory` 计划数据、实际下发的目标序列、带采样时间的关节反馈、执行器状态。
- 逐关节图：位置（rad）、速度（仅当可可靠估算或测得）、跟踪误差（rad）、时间偏差、采样间隙。
- 指标：最大绝对误差、RMSE、最终误差、执行持续时间、有效采样率、丢样比例；注明是否为真实反馈。
- 只有存在足够时间同步证据才计算跨设备延迟；否则标为估计或不可用。
- **验收**：用固定离线数据集独立复算指标；回放过程中不会触发任何硬件命令。

### FR-08 实验记录与导出（P1）

- 支持实验 `experiment_id`、试验 `trial_id`、成对试验 `pair_id`、方法、顺序、样本条件、成功/失败及连续误差指标。
- 失败代码最少覆盖：通信、超时、限位、规划失败、轨迹执行、视觉定位、标定、抓取失败、未知。
- 支持厂商 Baseline 与自研方法的同条件对照；禁止仅凭少量二元成功率宣称显著改善。
- **验收**：导出的 CSV 可用脚本重算主要指标；JSON 元数据完整；实验可追溯到对应日志和原始数据。

### FR-09 3D 模型与 TF（P2）

- 加载经过审计的 URDF；显示关节、TF、相机坐标系、目标姿态和模型限位。
- 模型状态与真实反馈明确区分；URDF 未验证时显示警示。
- **验收**：TF 缺失/循环/过期能提示；渲染失败不影响控制安全链路。

### FR-10 相机调试（P2）

- 展示相机画面、时间戳、分辨率、目标检测结果与坐标系来源；支持保存标定样本引用。
- 视觉叠加必须标注坐标系和变换版本，禁止将未经验证的估计作为地面真值。
- **验收**：相机掉帧、标定缺失、TF 过期均明确提示。

## 6. 安全需求（不可降级）

**安全原则**：浏览器只是操作入口；后端和机器人侧必须独立实施限位、超时、控制权和故障策略。物理急停/电源切断必须由硬件方案保障，不能依赖 HTTP、WebSocket 或 Python 线程及时响应。

- **SR-01 默认拒绝运动**：未完成硬件检查、关节映射校验、限位验证、控制权申请，不可发运动命令。
- **SR-02 服务器侧校验**：所有运动参数由机器人侧可信控制服务再次验证，不能只依赖前端。
- **SR-03 超时与看门狗**：SDK 阻塞读取须由隔离/有界调用策略包裹；看门狗由能实际影响执行的机器人侧实现。软件超时不等于电机已停止。
- **SR-04 故障锁存**：关键故障发生后锁存，需人工确认并重新安全检查；禁止自动重试运动命令。
- **SR-05 限位与环境**：关节机械限位须实机测量；规划碰撞检查不替代物理工作区防护。
- **SR-06 停止语义**：区分“停止请求已发送”“控制器确认”“运动实际停止”“物理断电”。无法验证时显示未知。
- **SR-07 网络访问**：默认绑定 localhost 或可信局域网；远程访问需要身份认证、TLS/可信隧道、控制权审计。公网直接暴露运动 API 禁止。
- **SR-08 模式隔离**：Simulation/Replay 与 Live 使用不同后端适配器；Replay 代码路径不具备硬件写权限。
- **SR-09 实验安全**：无人值守执行在独立风险评审和恢复测试通过前禁止。
- **SR-10 单一串口所有者**：任何时刻一个进程独占控制板串口，避免厂商工具与新系统冲突。

**安全验收场景**：网络断开、浏览器关闭、后端崩溃、驱动退出、反馈超时、串口断开、非法目标、重复点击、控制权争用、未知关节 ID、恢复后误动作、急停后重新使能。每个场景都需明确“命令是否被拒绝、机械臂实际如何响应、证据来自哪里”。

## 7. 系统架构与职责边界

```text
React + TypeScript UI
  │  HTTPS / WebSocket (status, events; not real-time servo loop)
  ▼
FastAPI Gateway / Session / Audit / Experiment API
  │  ROS 2 interface adapter (rclpy or bridge)
  ▼
ROS 2 Control Gateway / Trajectory Adapter (Python or C++ as measured)
  │  exclusive command arbitration + safety validation
  ▼
Vendor ROS 2 Driver (inspect before reimplementing)
  │
Vendor Python SDK (ros_robot_controller_sdk.py)
  │  pyserial / protocol
  ▼
STM32 / Bus Servos
```

**设计决策**：首版优先复用厂商 ROS 2 Driver 和 Python SDK；React + TypeScript 前端，FastAPI 网关，WebSocket 状态推送，SQLite 记录元数据，CSV/JSON 与 rosbag2 保存实验数据。Plotly 绘制轨迹；Three.js / React Three Fiber 仅 G4 引入。C++ `rclcpp` 轨迹适配器为可选实现，必须先检查厂商是否已有相同功能；不为“语言统一”而重写 SDK。

**接口约束**：Web API 不直接透传任意串口命令；使用明确的业务动作和结构化验证结果。FastAPI 只允许通过唯一 ROS 2 控制网关写入；ROS 2 通信层负责硬件控制。WebSocket 推送可丢帧/降采样，但原始实验数据记录须有独立可靠路径。

**部署待决**：机器人主控运行 Driver/Gateway、R9000P 运行 UI/分析，或全部运行在同一主机；由基准测试决定。前端应不依赖固定 IP；机器人侧服务不可依赖远端浏览器存活。

### 7.1 数据契约（建议字段）

RobotState:

单位约定：位置 `rad`、时长 `s`、延迟 `ms`、物理位移 `mm`；时间戳统一携带时钟来源。未知数据用 `null` + 原因，不填 0。

### 7.2 状态与控制权

- 状态采集链路与运动命令链路逻辑分离；只读用户永远无写权限。
- `Ready` 仅表示**满足本系统定义的运动前置条件**，不是整机绝对安全认证。
- 命令状态必须由反馈或驱动证据支撑；SDK 写入成功不等于关节达到目标。
- 一个控制源持有可撤销租约；紧急停止请求可绕过普通控制权，但其执行结果仍需验证。

## 9. 数据与实验设计

- 原始记录与衍生指标分开保存；所有计算结果记录算法版本。
- 时间对齐需明确 ROS Time、系统墙钟和单调时钟的区别；跨机器时钟同步能力要测量。
- 数据记录策略：短期实时环形缓冲 + 可持久化事件日志 + 实验原始数据文件；存储满时应提示并安全降级，不能静默丢失关键事件。
- 实验类型：关节重复性、方向回差、标定验证、视觉相对位移、抓取容差与成功率。
- 支持 Baseline vs Intervention 的配对比较、随机顺序、`pair_id`、失败代码与连续误差指标；二元抓取成功率为辅助结果。
- 结果图必须标注单位、样本数、排除条件、置信区间（适用时）及数据来源。

## 11. 测试与质量门禁

**测试金字塔**：单位测试（映射/限位/状态机/指标）→ 模拟驱动集成测试（故障注入）→ ROS 2 集成测试（接口/控制权）→ 低风险实机测试（人工看护）→ 重复性与回归测试。

**必须覆盖的负向测试**：超限、错误单位、NaN/Inf、未知 ID、过期反馈、断网、串口断开、重复请求、控制权抢占、回放误触发、SDK 阻塞、状态不同步、时钟跳变、存储写入失败、设备重启。

**交付完成定义（DoD）**：

1. 需求与接口契约更新，标明已实现/已验证/计划中。
2. 自动化测试通过并附测试输出；关键安全功能有负向测试。
3. ROS 2/SDK 依赖、环境和运行方式可复现。
4. 实机功能有操作步骤、风险评估、可观察证据与失败回滚方案。
5. 无未经授权的硬件动作；无默认自动重连后执行。
6. 代码评审与 QA 结论明确，阻断缺陷不得以“已知问题”绕过。

## 17. 产品原则（不可偏离）

1. **Observe before Act**：先看清状态，再允许动作。
2. **Safety before Convenience**：任何便捷交互不得绕过机器人侧保护。
3. **Evidence over Appearance**：曲线和状态必须有可追溯数据源，不展示虚假精度。
4. **Reuse before Rewrite**：优先复用 SDK/ROS 2/MoveIt 2，新增代码必须解决真实缺口。
5. **Offline before Hardware**：先 Mock/Replay，再有人看护的实机测试。
6. **Debuggability is a Feature**：每个失败都应留下足以定位的证据。
7. **Research-ready by Design**：数据结构从第一天支持后续误差预算和配对实验。
8. **Scope Discipline**：不得为 3D 外观、AI 功能或移动底盘牺牲核心调试可靠性。

> **最终验收定义**：不是“页面能让机械臂动”，而是“开发者能在可控风险下发送命令、观察真实反馈、定位异常、复现实验，并用数据证明系统行为”。
